
-Goal-
Given a text document that is potentially relevant to this activity and a list of entity types, identify all entities of those types from the text and all relationships among the identified entities.

-Important note on structured/tabular numeric data-
Some input text may consist primarily of tabular numeric records (for example, earthquake catalog rows with fields such as date, time, latitude, longitude, depth, and magnitude, rather than narrative prose). When this is the case, build the hierarchy SEQUENCE -> CLUSTER -> EVENT:
- EVENT (bottom level): treat each individual record (e.g., each earthquake) as one EVENT entity. Its entity_description must state its date/time, latitude, longitude, depth, and magnitude exactly as given, each correctly attributed to the right field -- never substitute one numeric field for another (e.g., never report a latitude or longitude value as if it were a magnitude, or vice versa).
- CLUSTER (middle level): within the chunk, group EVENTs into one or more CLUSTER entities based on genuine, directly observable spatio-temporal proximity -- events that are close together in both time (e.g., within minutes to a few hours of each other) and space (e.g., within about 10 km of each other) belong in the same cluster; events far apart in time or space belong in different clusters. Do not force every event in the chunk into a single cluster if the data does not support it, and do not split events that are clearly close together into separate clusters. This grouping is a purely factual, directly observable operation (proximity in time and space is computable from the given numbers), which is different from what comes next.
  Its entity_description must state only directly computable facts: the number of events, the time range, the spatial extent, the magnitude range, and which single event has the largest magnitude in the group (stated neutrally, e.g., "the largest event in this group is EVENT <name>, M<x>" -- do not call it a "mainshock" or claim it caused or will cause anything unless the text says so; a magnitude comparison is not, by itself, evidence of a physical relationship).
- Do not classify a CLUSTER or SEQUENCE using seismological terminology (e.g., "mainshock", "aftershock", "foreshock", "swarm", "doublet", "triplet", "multiplet", "triggered", "induced") based on the numeric shape of the data alone -- these are scientific interpretations that require independent evidence (established statistical methods applied to the whole catalog, or a domain expert's or the literature's own characterization), not something a single window of raw numbers can establish by itself, and guessing from the shape of the numbers alone is exactly the kind of unsupported inference this pipeline must avoid. Only attach any such term to an entity when the input text you are given itself explicitly uses that term (or an unambiguous paraphrase of it) to describe specific events, a cluster, or the sequence -- in that case, quote or closely paraphrase the text's own characterization in the entity_description and attribute it to the text (e.g., "described in the text as the mainshock of this sequence"), rather than presenting it as your own inference. If the text is purely numeric with no such description, leave the CLUSTER's description purely factual as specified above and do not add any classification.
- SEQUENCE (top level): a "sequence" is a scientific grouping, not an artifact of how the text happens to be split into chunks -- treat the entire input document (not just the current chunk) as belonging to a single SEQUENCE, and always name it SEQUENCE, using that exact same name in every chunk you process from this document. Only deviate from this if the text itself explicitly describes two or more distinct, separately named sequences or phases (e.g., "the foreshock sequence" vs. "the mainshock-aftershock sequence") -- in that case, use the names given in the text instead of SEQUENCE, and use them consistently across chunks. Do not invent a new sequence name for each chunk just because the chunk covers a different time window; GraphRAG will automatically merge every chunk's mention of the same SEQUENCE name into a single node, so consistent naming across chunks is what connects the whole document together. Every CLUSTER you identify must be linked via "containsCluster" to the relevant SEQUENCE.
- FAULT: only create a FAULT entity if the input text explicitly names a specific fault or fault system. Purely numeric rows (latitude/longitude/depth/time/magnitude only) never contain this information by themselves -- in that case, do not create a FAULT entity and do not guess or infer one from general background knowledge about the region. If the text does explicitly name a fault, link the SEQUENCE to it via "occursOn".
- GEO (GeographicRegion): only create a GEO entity if the input text explicitly names a broader geographic or tectonic region (e.g., "Mojave Desert", "Sichuan-Yunnan border region", "northeastern margin of the Tibetan Plateau") -- this is a larger-scale area, distinct from FAULT, which is a specific rupture structure. Purely numeric rows never contain this information by themselves -- do not create a GEO entity and do not guess or infer one from general background knowledge about where the coordinates might be. If the text does explicitly name a region, link the SEQUENCE to it via "isLocatedIn".
- FACILITY: only create a FACILITY entity if the input text explicitly names a specific human activity or installation that could plausibly relate to induced seismicity (e.g., a named reservoir, water injection well, mine, or geothermal operation). Purely numeric rows never contain this information -- do not create a FACILITY entity and do not guess or infer one (e.g., from knowing that a region generally has reservoirs or wells). If the text does explicitly name such a facility, link the relevant CLUSTER (or the SEQUENCE, if the text describes the facility as relevant to the whole sequence rather than one specific cluster) to it via "occursNear", with the relationship_description stating what the text says about the connection (e.g., "text describes this cluster as of probable induced origin, adjacent to this reservoir").
- Every EVENT must be linked to its CLUSTER via a "containsEvent" relationship, and every CLUSTER must be linked to its SEQUENCE via "containsCluster" -- do not leave any EVENT or CLUSTER unconnected. In addition, extract direct EVENT-to-EVENT relationships only when they reflect a genuine, directly observable pattern: "occursNear" for events explicitly close in space; "precedes"/"follows" for direct chronological adjacency worth noting. Do not extract a "triggers" (or any other causal) relationship between two EVENTs based on numeric proximity alone -- only do so if the input text explicitly states that one event triggered, caused, or was followed by another as a described relationship. Do not invent relationships that are not supported by explicit or directly computable proximity in time and/or space (for occursNear/precedes/follows) or by explicit textual statement (for triggers or any classification-bearing relationship).
- If a chunk of text does not clearly fit any of the given entity types, simply extract fewer entities (or none) rather than inventing a category. Never output your own reasoning, uncertainty, or commentary about the data as if it were an entity, entity_type, or description -- your entire output must consist only of well-formed ("entity"...) and ("relationship"...) tuples as specified below, with no additional prose before, between, or after them.

-Steps-
1. Identify all entities. For each identified entity, extract the following information:
- entity_name: Name of the entity, capitalized
- entity_type: One of the following types: [{entity_types}]
- entity_description: Comprehensive description of the entity's attributes and activities
Format each entity as ("entity"{tuple_delimiter}<entity_name>{tuple_delimiter}<entity_type>{tuple_delimiter}<entity_description>)

2. From the entities identified in step 1, identify all pairs of (source_entity, target_entity) that are *clearly related* to each other.
For each pair of related entities, extract the following information:
- source_entity: name of the source entity, as identified in step 1
- target_entity: name of the target entity, as identified in step 1
- relationship_description: explanation as to why you think the source entity and the target entity are related to each other
- relationship_strength: a numeric score indicating strength of the relationship between the source entity and target entity
 Format each relationship as ("relationship"{tuple_delimiter}<source_entity>{tuple_delimiter}<target_entity>{tuple_delimiter}<relationship_description>{tuple_delimiter}<relationship_strength>)

3. Return output in English as a single list of all the entities and relationships identified in steps 1 and 2. Use **{record_delimiter}** as the list delimiter.

4. When finished, output {completion_delimiter}
